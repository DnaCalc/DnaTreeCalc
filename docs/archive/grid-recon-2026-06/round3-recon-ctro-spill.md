## 2. CTRO in code (OxCalc, shipped)

- **Descriptor kinds**: `TreeReference::DynamicPotential {carrier_id, detail}` (unresolved-until-calc) and `DynamicResolved {target_node_id, ...}` — `OxCalc\src\oxcalc-core\src\formula.rs:71-79`; both lower to `DependencyDescriptorKind::DynamicPotential` (`formula.rs:3300-3301`, `dependency.rs:28`).
- **Runtime flow** (`treecalc.rs` run loop):
  1. Static graph from `BoundFormula` descriptors (`treecalc.rs:875-876`).
  2. **Positive publication**: prior-run CTRO edges arrive as publication runtime effects and are merged into this run's *invalidation* graph (`treecalc.rs:877-887`).
  3. Per-node eval via `evaluate_with_oxfml_session` with **working values** (`treecalc.rs:1186-1191`); a `TreeCalcReferenceSystemProvider` is built per evaluation over those working values and attached to the OxFml session (`treecalc.rs:4769-4795`).
  4. `resolve_text` (INDIRECT lane) resolves the text against the structural snapshot and **records** a `TreeCalcRuntimeReferenceTextResolution` (`tree_reference_system.rs:214-269`); harvested after invoke (`treecalc.rs:4808`, `:1203-1204`).
  5. Post-loop: resolutions → diagnostics `ctro_reference_text_resolution:...` (`treecalc.rs:1311-1323`) → `ctro_dynamic_ref:` descriptors (`treecalc.rs:2294-2300`) → **effective graph rebuilt** (`treecalc.rs:1337-1350`) → dependency-shape updates published, edges persisted as `published_ctro_dynamic_ref` runtime effects for the next run (`treecalc.rs:2316-2322`).
- **Crucial semantics**: there is **no within-run re-entry**. A CTRO-discovered edge changes invalidation/scheduling on the *next* run; within the run the dereference reads whatever working/published value exists (`tree_reference_system.rs:168-197` — missing value = `ProviderFailure`, not interruption). Convergence is run-over-run.
- Rebind fact roles (`tree_reference_rebind.rs:22-43`, `:420-431`): DynamicPotential is a `RuntimeFact`, not a structural edge. Canonical tests: `consumer.rs:14875` (INDIRECT records CTRO edge), `:15050` (static `{A,B,A}` vs dynamic `INDIRECT`).

## 3. OxFml spill machinery

- **Binding**: `ReferenceExpr::Spill { anchor }` (`OxFml\crates\oxfml_core\src\binding\reference.rs:201-203`). Semantics pass sets `uses_spill_reference`, `requires_reference_preservation`, pushes `EvaluationRequirement::SpillReference` + capability `"spill_reference"` (`semantics\mod.rs:439-445`). Carrier gating: `SpillReferenceOperatorNotAdmitted` for restricted carriers (`carrier.rs:188-194`). `ImplicitIntersection` is a `BoundExpr` wrapper (`binding\mod.rs:187,458`); `_XLFN.SINGLE`/`SINGLE` maps to it (`semantics\mod.rs:816-821`) and to `LegacySingle` call class (`eval\mod.rs:447`); it is caller-context-sensitive at eval (`eval\mod.rs:5570,5604`).
- **Eval**: `A1#` compiles to an `OP_SPILL_REF` reference-operator call (`eval\mod.rs:1405-1408`, dispatch `:3561-3569` → `evaluate_reference_operator_call:3623`). OxFunc `op_spill_ref.rs:56-73` merely normalizes the anchor and returns `ReferenceLike(ReferenceKind::SpillAnchor, "Sheet1!B2#")` — **no extent computation anywhere**. Dereference of a `SpillAnchor` is wholly delegated to the `ReferenceSystemProvider` (capability `allow_spill_anchor_refs`, `OxFunc\...\resolver.rs:11,586`) — and **no provider implements it** (zero `SpillAnchor` matches in OxFml src; OxCalc's TreeCalc provider has none). `CompositeReferenceOperation::SpillExpansion` exists only as a compose-op key (`resolver.rs:389`).
- **Seam types** (`OxFml\...\seam\mod.rs`): `Locus{sheet_id,row,col}` (:5), `Extent{rows,cols}` (:11), `ValueDelta.result_extent` (:41), `ShapeDelta{anchor_locus, intended_extent, published_extent, blocked_loci, shape_outcome_class}` (:53-62), `SpillFact` (:74-81), `TopologyDelta.spill_facts` (:117), `SpillEventKind{SpillTakeover,SpillClearance,SpillBlocked}` (:140-144), `SpillEvent` (:146-156), `RejectCode::StructuralConflict` (:207).
- **Typed vs aspirational**: `session\mod.rs:1006-1125` (`build_candidate_result`) computes extent from the OxFunc value shape and emits a `SpillTakeover` whenever extent >1×1 — **always** with empty `blocking_loci`, `ShapeOutcomeClass::Established`, and `spill_facts: Vec::new()` (:1113). `SpillBlocked`, `SpillClearance`, `Blocked`, `blocked_reason_class` are **never produced in src** (only test fixtures, `replay_fixture_tests.rs:1250-1259`). So: extent *reporting* is real; blockage detection and commit arbitration are vocabulary only.

## 6. Gap list for grid spill (ownership today → needed)

1. **Extent resolution**: extent exists only as a value-shape fact in OxFml's candidate (`session\mod.rs:1015-1017`). Nobody maps extent → grid cells. Needed: OxCalc grid-profile spill placement (anchor Locus + Extent → region in the sheet facet). *Engine (OxCalc grid profile)*.
2. **Blockage detection / #SPILL!**: no producer of `SpillBlocked`/`Blocked` anywhere. Needs calc-time occupancy check (literals, other spills, overrides) and feedback of `WorksheetErrorCode::Spill` (`oxfunc_value_types\lib.rs:28`) into the anchor's published value — a host-veto→re-value loop the seam lacks (candidate built once, commit never arbitrates shape). *Engine-owned decision; OxFml seam extension for the veto path.*
3. **Spill-range refs via CTRO**: `OP_SPILL_REF` produces `SpillAnchor` references no provider can dereference. Needed: grid provider `dereference`/`enumerate_values` for `SpillAnchor` resolving the *current* extent, plus a DynamicPotential edge consumer→current-spill-region published through the existing positive-publication lane (`treecalc.rs:2294-2322` pattern). This is exactly the CTRO mechanism — it generalizes from "value-dependent target identity" (INDIRECT) to "value-dependent target *extent*", which W047's frontier-repair doc anticipates ("region/spill resize") but nothing implements. *OxCalc provider + CTRO; OxFml pass-through only.*
4. **Re-spill on edit**: needs reverse map cell→owning anchor so edits inside a spill region invalidate the anchor (block→#SPILL!) and clears re-expand it; invalidation seeds from non-formula edits. DnaVisiCalc's overlay-ownership model is the proven shape. *Engine grid state + scheduling.*
5. **Within-run staleness**: CTRO converges next-run (no re-entry, §2). Spill resize mid-run can hand `A1#` consumers stale extents; choose iterate-to-fixpoint vs in-run frontier repair (W047 doc specifies semantics, lines 191-201, implementation chose neither). *Engine.*
6. **Implicit intersection**: machinery complete in OxFml/OxFunc but needs grid `CallerContext` (row/col, `resolver.rs:16-20`) supplied by the provider. *OxCalc grid profile.*
7. **Seam adoption**: `Locus`/`Extent`/`ShapeDelta`/`SpillEvent` are already grid-shaped and host-meaningless for TreeCalc; the grid profile can adopt them directly, but producers must graduate from always-`Established` placeholders to real arbitration. *OxFml types stay; OxCalc/host produce truthfully.*

**Ownership summary**: OxFunc = value/error/reference vocabulary + provider traits (done). OxFml = syntax (`#`, `@`), requirement/capability gating, seam fact types (done as vocabulary; emits facts mechanically, never arbitrates). OxCalc = CTRO engine (shipped for INDIRECT/TreeCalc), providers (TreeCalc shipped, grid absent), spill placement/blockage/commit (absent). Host = consumes nothing spill-related today.

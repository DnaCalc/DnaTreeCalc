# OxCalc Engine Architecture Map (read from C:/Work/DnaCalc/OxCalc main checkout)

Active implementation is the Rust workspace `src/` with crates `oxcalc-core`, `oxcalc-tracecalc`, `oxcalc-tracecalc-cli` (`src/README.md`). All structure below is `oxcalc-core` (~68k LOC, no `unsafe`, no threading primitives anywhere).

## 1. Core node/tree model

- **Node identity**: `TreeNodeId(pub u64)` — `src/oxcalc-core/src/structural.rs:12`. Node kinds: `StructuralNodeKind { Root, Container, Calculation, Constant }` (structural.rs:48). A `StructuralNode` (structural.rs:56) is `{node_id, kind, symbol: String, parent_id: Option<TreeNodeId>, child_ids: Vec<TreeNodeId>}` — a named tree, not a grid.
- **Storage**: `StructuralSnapshot` (structural.rs:202) = `BTreeMap<TreeNodeId, StructuralNode>` + `path_index: BTreeMap<String, TreeNodeId>` (full projection-path → id index, rebuilt on every snapshot build, structural.rs:559). Snapshots are immutable; `apply_edit` clones the whole node map via `StructuralSnapshotBuilder::new(Some(self))` (structural.rs:388–478, 631) and revalidates + rebuilds the path index per edit — O(n log n) per structural edit.
- **Values** live outside the structural tree: published values are `BTreeMap<TreeNodeId, CalcValue>` (`CalcValue` comes from `oxfunc_core::value`, treecalc.rs:36–38) held in `PublishedRuntimeLayerPayload { values_by_node, value_epochs_by_node, runtime_effects }` (consumer.rs:803–809) per workspace; literal inputs in a `node_input_snapshot` on `WorkspaceRevision` (treecalc.rs:160–179). Run output: `LocalTreeCalcRunArtifacts.published_calc_values: BTreeMap<TreeNodeId, CalcValue>` (treecalc.rs:488).
- **Table node model** (the closest thing to a grid today): tables are a *facet on a node*, not a node kind. `StructuralEdit::SetTableShape` attaches `StructuralTableShape` (structural.rs:65–78) carrying identity/version strings (`row_membership_version`, `column_identity_version`, `virtual_anchor_identity`…). The full model is `TreeCalcTableNodeSnapshot` (`structured_table.rs:132–151`): `rows: Vec<TreeCalcTableRowId>` (string row ids, order = row order), `columns: Vec<TreeCalcTableColumnSnapshot>` with `body_metadata: ConstantCells | Formula(TreeCalcTableFormulaMetadata)` (one R1C1-style formula per column, evaluated per row — structured_table.rs:90–116, `evaluate_treecalc_table_column_formula_rows` structured_table.rs:3501), plus **optional** per-cell node bindings `body_cell_nodes: Vec<TreeCalcTableBodyCellNodeBinding {row_id, column_id, node_id}}` (structured_table.rs:119–123) — i.e., cells are *virtual by default* and only selectively materialized as tree nodes. `TreeCalcTableVirtualAnchor {workbook_scope_ref, sheet_scope_ref, start_row: u32, start_col: u32}` (structured_table.rs:51) is the only sheet/A1-flavored coordinate in the engine. The DnaTreeCalc handover (`C:/Work/DnaCalc/DnaTreeCalc/docs/handovers/HANDOVER_OXCALC_table_node_model.md`) asks exactly how this lowers — the answer in code is: column formulas + structured-table dependency descriptor kinds + sparse readers (below), no Table value in OxFunc.

## 2. Dependency graph & dirty propagation

- `DependencyDescriptor` (dependency.rs:36) — string `descriptor_id`, owner/target `TreeNodeId`, `kind: DependencyDescriptorKind` (dependency.rs:13–33: `StaticDirect`, `RelativeBound`, collection-membership, 10 structured-table kinds, `DynamicPotential`, `HostSensitive`, `Unresolved`…).
- `DependencyGraph` (dependency.rs:246–254): `descriptors_by_owner`, `edges_by_owner`, `reverse_edges` all `BTreeMap<TreeNodeId, Vec<DependencyEdge>>`; `workspace_reverse_edges: BTreeMap<String,…>` for cross-workspace; `cycle_groups` via recursive Tarjan (dependency.rs:579–660). **Edges carry heap `String` edge_ids/descriptor_ids and are cloned into reverse_edges** (dependency.rs:420–427) — heavy per-edge allocation.
- **Rebuilt from scratch every run**: `LocalTreeCalcEngine::execute` (treecalc.rs:788) prepares all formulas, lowers descriptors, calls `DependencyGraph::build` (treecalc.rs:845), possibly builds it **twice** when published dynamic deps exist (treecalc.rs:851–857). There is no persisted incremental graph.
- **Dirty propagation**: `derive_invalidation_closure(&[InvalidationSeed])` (dependency.rs:450) — BFS over `reverse_edges` producing `InvalidationClosure { impacted_order, records: BTreeMap<TreeNodeId, NodeInvalidationRecord> }` with per-node `NodeCalcState` (recalc.rs:12: Clean/DirtyPending/Needed/Evaluating/VerifiedClean/PublishReady/RejectedPendingRepair/CycleBlocked) and `requires_rebind`. `InvalidationReasonKind` (dependency.rs:257) includes structured-table row/column/region reasons.
- **Incremental edit handle**: `OxCalcTreeContext` (consumer.rs:836) — workspaces (`OxCalcTreeWorkspaceState`, consumer.rs:741–768) accumulate `pending_invalidation_seeds`/`pending_dependency_shape_updates`, edits via `OxCalcTreeEditTransaction` of `OxCalcTreeEdit` (consumer.rs:297–338: AddNode/SetNodeInput/SetNodeFormulaText/SetNodeTable/Rename/Move/Delete…) with `TransactionRecalcPolicy::{RecalculateAndPublishOnce, ApplyOnly}` (consumer.rs:347). Revision retention + candidate overlays (speculative layered workspaces, consumer.rs:789–801) exist. `OxCalcTreeInvalidationPlan` preview (consumer.rs:533) exposes dirty set + evaluation order without running.
- **Edge cache**: `EdgeValueCache` (value_cache.rs:173) — `BTreeMap<EdgeValueCacheKey{call_site_id: String, hole_binding_fingerprint: String}, EdgeValueCacheEntry{value_payload: String,…}>`, bounded FIFO eviction, excluded for volatile/effectful paths. Cache basis is a giant formatted string of snapshot ids (treecalc.rs:211–220). Note ROADMAP finding: warm no-op runs were 10–80× slower than cold *via* `EdgeValueCacheLookup`/`DiagnosticSeedCollection` (DnaTreeCalc `docs/ux/stack-requirements/ROADMAP.md:206–210`).

## 3. Formula attachment & OxFml consumption

- `TreeFormula` (formula.rs:2490): opaque OxFml `source_text` + `explicit_references: Vec<TreeReference>` + optional `bound_formula: Option<oxfml_core::binding::BoundFormula>`. Attached via `TreeFormulaBinding {owner_node_id, formula_artifact_id, bind_artifact_id, expression}` in `TreeFormulaCatalog: BTreeMap<TreeNodeId, TreeFormulaBinding>` (formula.rs:2697–2716) — **one binding per node, no template sharing**. `TreeFormulaCatalog::to_dependency_descriptors` lowers references per binding (formula.rs:2734).
- Per run, `prepare_oxfml_formula` is called for **every** binding (treecalc.rs:798–811), constructing a `FormulaSourceRecord::new(formula_artifact_id, owner_node_id.0, source_text)` (treecalc.rs:3036) and driving `OxfmlRecalcSessionDriver` (oxfml_session.rs:26) → OxFml `RuntimeSessionFacade` phases (recalc_wave.rs:17–25: WavePreparation → EnsurePrepared → Compilation → DependencyDerivation → ScheduleInvoke → CoordinatorCommit → CloseCapture).
- **Dedup today**: only OxFml-session-level artifact reuse — repeated identical requests reuse green tree / red projection / bound formula / semantic plan (test oxfml_session.rs:163–179), and `PreparedFormulaIdentityTrace` (treecalc.rs:567) records identities. But keying includes owner node id, and preparation is re-run per node per recalc — there is **no R1C1-template interning across nodes**. The one true shared-formula construct is the table **column formula** (one formula, per-row evaluation, structured_table.rs:3501) — the existing precedent for repeated-formula regions.

## 4. Reference model / addressing

- Addressing is id + hierarchical-path based, no A1/R1C1: `TreeReference` (formula.rs:26–83) = `DirectNode{target_node_id}`, `ProjectionPath{“Root/Branch/Leaf”}`, `RelativePath{base: SelfNode|ParentNode|Ancestor(n)}`, `SiblingOffset` (the @PREV/@NEXT substrate), collections (`ChildrenV1`, ordered selectors Siblings/Preceding/Following/Ancestors/RecursiveDescendants, formula.rs:86–144), `CrossWorkspaceResolved`, `DynamicPotential/Resolved`, `HostSensitive`, `Unresolved`.
- “Sheets” ≈ workspaces (`OxCalcTreeWorkspaceId(String)`, consumer.rs:163) with cross-workspace edges. “Ranges” ≈ reference collections plus the sparse-reader substrate: `SparseCellCoord{row: u32, column: u32}`, `SparseRangeExtent`, `SparseCellRead::{Defined(CalcValue), Blank}`, `SparseRangeReader` (sparse_reader.rs:17–110) — a 2D sparse-cell read abstraction already used to feed OxFml range semantics from tree collections and table sections (`TreeCalcTableSparseReader` structured_table.rs:2973, sections `#Headers/#Data/#Totals` structured_table.rs:1875).

## 5. Threading & perf

- **Strictly single-threaded sequential Stage 1**: zero matches for `rayon|thread|Mutex|RwLock|Arc` in `src/`. `LocalTreeCalcEngine::execute` is a pure function of an owned input (confirmed by passivity spike, ROADMAP.md:202–206); Stage 2 partitioned-parallel is design-only (README.md:9, TLA models in docs/spec).
- **Measured** (docs/test-runs/core-engine/treecalc-scale/BASELINE_2026-05-04.md): 1M nodes/1M formulas/2M edges = **6.9 s** total, dominated by model+descriptor+graph build (~5.4 s); 16M edges → 40 s graph-dominant; relative-rebind churn pathological at **337 s** soft-reference update; ~11.2 GB working set at 1M nodes/8M edges (≈11 KB/node-edge mix).
- **Host-observed blocker** (DnaTreeCalc `docs/ux/skin-suite/PHASE_B.md:12,56-57`): real end-to-end recalc is *quadratic-or-worse* (1k nodes ≈ 4 min cold; warm no-op 10–80× slower than cold). Acceptance: chain n=5k cold ≤ ~1 s release, warm strictly cheaper, incremental cost ∝ dirty set. The in-flight `calc-perf` worktree targets this (bead `calc-ekq3`).

## 6. Grid extension seams & breaking assumptions

Seams that already point the right way:
- **Virtual cells**: `TreeCalcTableNodeSnapshot` proves the pattern — bulk region as one node-facet, per-cell `TreeNodeId` bindings only where needed (structured_table.rs:132–151). A `Sheet/Grid` container would most naturally be a sibling facet (like `SetTableShape`, structural.rs:144) or a new `StructuralNodeKind` whose occupants are sparse blocks, not children.
- **2D sparse reads**: `SparseRangeReader`/`SparseCellCoord` (sparse_reader.rs) is the ready-made value-surface for ranges and a rendering/streaming pass.
- **Viewport-driven recalc**: `LocalTreeCalcSchedulingPolicy::PushVisibilityBounded{visible_observer_node_ids}` (treecalc.rs:454–460; plan at treecalc.rs:2654–2750) already does observer-upstream-closure scheduling with declared semantic equivalence + starvation caveats (treecalc.rs:8392–8395).
- **Shared formulas**: column-formula-per-row evaluation (structured_table.rs:3501) is the template for R1C1-identical regions.

Assumptions that break at 10^7+ cells:
1. Every node in `BTreeMap` + `Vec<child_ids>` + `String` symbol + full `path_index` of owned path strings (structural.rs:202–209) — and **snapshot-per-edit clones the entire map** (structural.rs:631).
2. Every formula = one `TreeFormulaBinding`, re-prepared through OxFml every run (treecalc.rs:798); no template dedup.
3. Dependency graph fully rebuilt per execute, with per-edge `String` ids and cloned reverse edges (treecalc.rs:845; dependency.rs:300–447); descriptor identity/version carriers are formatted strings embedding full member-id lists (dependency.rs:88–96 — O(members) strings).
4. `Stage1RecalcTracker::new` materializes a state entry for every node (recalc.rs:80–92); `LocalTreeCalcInput` carries whole-workspace `BTreeMap<TreeNodeId, CalcValue>` publication values by value (treecalc.rs:144).
5. Artifact/compatibility bases serialize the entire formula catalog + descriptor set to JSON strings per run (treecalc.rs:223–318).
6. Identity/version tokens everywhere are heap strings (`FormulaArtifactId(String)`, structural.rs:30) — interning is absent.

Spec/equivalence machinery the user's "simple-correct vs optimized pair" can reuse: TraceCalc reference machine + conformance oracle (`src/oxcalc-tracecalc`, docs/worksets/W012), Lean/TLA formalization lanes (docs/spec/core-engine/w033–w036), metamorphic scale semantic binding (W033_METAMORPHIC_SCALE_SEMANTIC_BINDING.md), and the closed-form-checked scale runner `treecalc_scale.rs` (`TreeCalcScaleProfile`, line 32).

## 1. Microsoft Excel internals

- **Three-stage recalc: dependency tree → calculation chain → evaluate dirty cells.** Chain lists all formula cells in last-known-good order; during recalc, if a formula hits an uncalculated precedent, that cell *and its dependents are moved down the chain* — i.e., the chain is self-optimizing across recalc cycles ("calculation times often improve in the first few cycles after opening"). Dirty marking is transitive (edit A1 → B1, C1 dirty). Well-sourced: [Excel Recalculation (MS Learn)](https://learn.microsoft.com/en-us/office/client-developer/excel/excel-recalculation).
- **MTR (Excel 2007+):** Excel partitions the calc chain into independent sections run on up to 1024 configurable threads; cells/functions must be declared thread-safe (XLL `$` annotation); data tables are explicitly *not* MTR. Well-sourced: [Multithreaded Recalculation in Excel](https://learn.microsoft.com/en-us/office/client-developer/excel/multithreaded-recalculation-in-excel). Patent detail on chain-splitting/dependency levels: [US7533139](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/7533139), [US8032821](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/8032821).
- **Volatile functions** (NOW, RAND, OFFSET, INDIRECT, conditionally CELL/INFO/SUMIF) re-dirty their dependents every cycle; async UDFs are parked and trigger a second calc pass on completion. Same MS Learn page. Control surface: `Range.Dirty`/`Range.Calculate`, CTRL+ALT+SHIFT+F9 full tree rebuild, `ForceFullCalculation`.
- **File-format evidence of sparse + template sharing:** `sheetData` stores only present rows/cells; cells carry `r` (address), `s` (style index into shared `cellXfs`), shared strings table; **shared formulas**: master cell holds `<f t="shared" ref="range" si="id">formula</f>`, clones store only `si` — Excel's own engineers state this exists for speed and single-point edit over e.g. 50,000 rows. Well-sourced: [MS-OI29500 §18.3.1.40 f element](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/b5d1f58c-b1a1-4fcd-aaa0-ee7f4e8af9de), [Brian Jones: shared formulas perf](https://learn.microsoft.com/en-us/archive/blogs/brian_jones/spreadsheet-performance-shared-formulas). `calcChain.xml` persists last calc order (dependency-sorted graph) so reopened books warm-start: [calcChain schema](https://schemas.liquid-technologies.com/officeopenxml/2006/calcchain.html).
- **Memory:** 32-bit Excel = 2GB VA shared with add-ins; LAA update raised to 3GB (32-bit OS)/4GB (WOW64); 64-bit has no hard limit — workbook memory can far exceed on-disk size. Well-sourced: [LAA change](https://learn.microsoft.com/en-us/troubleshoot/microsoft-365-apps/excel/laa-capability-change), [32-bit memory usage](https://learn.microsoft.com/en-us/troubleshoot/microsoft-365-apps/excel/memory-usage-32-bit-edition-of-excel), [Excel Memory Limits (Decision Models)](https://www.decisionmodels.com/memlimitsc.htm).
- **Empirical scaling datapoint:** 1M rows × 10 cells = 60MB xlsx / 20MB xlsb / ~400MB RAM (~37 bytes/cell observed), full recalc of 15M FLOP model in 0.57s single-machine — "brute force works when all data is in memory." Well-sourced (independent benchmark): [The World's Most Boring Spreadsheet](https://www.thecandidstartup.org/2023/01/30/boring-spreadsheet.html).

## 2. Sestoft (Corecalc/Funcalc) — read directly from the tech report PDF

[Corecalc/Funcalc home](https://www.itu.dk/people/sestoft/funcalc/); tech report [ITU-TR-2006-91](http://studwww.itu.dk/~sestoft/corecalc/ITU-TR-2006-91.pdf); book: [Spreadsheet Implementation Technology (MIT Press)](https://mitpress.mit.edu/9780262526647/spreadsheet-implementation-technology/). All bullets below well-sourced from the PDF itself:

- **Storage (§2.4):** `Sheet` = dense rectangular `Cell[,]`, null = inactive cell. Simple, not sparse — a known design simplification, with alternatives discussed in ch. 3.
- **Formula sharing (§2.5, §2.8):** copy/paste produces distinct `Formula` objects (per-cell cached value + flags) that **share one underlying `Expr` AST** ("virtual copies") because references are relative/absolute `RARef` in R1C1-style C0R0 form (4 forms: CcRr, CcR[r], C[c]Rr, C[c]R[r]). Insert/delete rows adjusts formulas while "preserving as much sharing of virtual copies as possible" via a `Dictionary<Expr,Adjusted<Expr>>` memo. Matrix formulas: cells hold (shared `CachedMatrixFormula`, local offset) — evaluate once, scatter components — a direct precedent for "virtual cell nodes."
- **Recalculation (§2.11):** full recalc, top-down recursive, each formula evaluated exactly once per cycle via two flags `visited`/`uptodate`; cycle detection = visited-but-not-uptodate. Linear in active cells; noted risk of deep recursion on long chains (suggested fix: fallback approximate topo-sort).
- **Minimal recalc analysis (§3.3):** event listeners and explicit support (dependents) graphs both blow up to O(N²) edges for SUM-pyramid patterns, while the *dependency* direction stays O(F) thanks to compact area references; volatile cells need a separate always-dirty list; static cycles may be dynamically harmless (non-strict IF).
- **Compressed support graph (ch. 4, the standout idea):** represent the dependents of a cell as **FAP sets** — finite arithmetic progressions (offset, period, cardinality) — and a "FAP grid" (column-FAP × row-FAP) per edge *family*, so the support edges created by copying one formula over a rectangular region cost O(1) space regardless of region size. Includes union/overlap algebra (lcm/gcd zip equivalences), maintenance under edit, and reconstruction. This is the closest published prior art for "repeated R1C1-identical formula regions" as first-class compressed graph structure.

## 3. Modern open-source engines

- **HyperFormula:** one graph node per cell *plus per-range nodes*; range `B5:D20` is built as composition of `B5:D19` + remaining cells, collapsing O(n²) range arcs to O(n) for associative functions (SUM/MAX/COUNT); topological order with dirty-only selective recalc; per-sheet choice of **dense vs sparse address-to-node mapping** (`AlwaysSparse` option); 3.2.0 removed JS `Map`-size limits, tested at 30M+ cells. Well-sourced: [dependency graph guide](https://hyperformula.handsontable.com/docs/guide/dependency-graph.html), [performance guide](https://hyperformula.handsontable.com/guide/performance.html), [3.2.0 blog](https://handsontable.com/blog/hyperformula-3.2.0-expanding-excel-parity-and-removing-scalability-limits).
- **IronCalc (Rust):** engine + xlsx read/write, wasm/server targets; public docs are thin on internals — sparse storage/dependency details would need a source read ([github.com/ironcalc/IronCalc](https://github.com/ironcalc/IronCalc), [docs.rs ironcalc_base](https://docs.rs/ironcalc_base/latest/ironcalc_base/)). Inference: per-sheet sparse maps keyed by row→column; not verified in this pass.
- **Univer:** plugin architecture spanning browser/Worker/Node; formula engine does lexing→AST→dependency analysis→execution queue, can run in Web Workers or server-side; custom Canvas rendering engine (RenderUnit per document). Well-sourced: [formula engine architecture](https://docs.univer.ai/guides/recipes/architecture/formula), [rendering architecture](https://docs.univer.ai/guides/recipes/architecture/rendering).
- **SheetJS:** sparse mode = cells as A1-keyed object properties; **dense mode** = `!data` array-of-arrays, documented as more memory-efficient for very large sheets in modern JS engines. Well-sourced: [sheet object docs](https://docs.sheetjs.com/docs/csf/sheet).
- **Calamine (Rust, read-only):** `Range` with `from_sparse` constructor (row-major sorted sparse cells) and start-offset semantics; memory guard via `UnzipXMLSizeLimit` spilling XML to temp. Well-sourced: [Range docs](https://docs.rs/calamine/latest/calamine/struct.Range.html), [repo](https://github.com/tafia/calamine).
- **LibreOffice Calc (strongest engine prior art beyond Excel):** since 4.x stores each column as `mdds::multi_type_vector` — typed element blocks (doubles, strings, formula cells) in a positional primary array, i.e., **columnar, run-typed storage** replacing per-cell heap objects ([Kohei Yoshida: multi_type_vector explained](https://kohei.us/2012/07/20/mdds-multi_type_vector-explained/), [benchmarks](https://kohei.us/2019/12/12/benchmark-results-on-mdds-multi_type_vector/)). Adjacent same-R1C1 formula cells form **formula groups** sharing one token array; groups are calculated as a unit with inputs gathered into packed vectors for the SIMD-ish software interpreter or OpenCL, plus threaded group calc ([Lillqvist, "Making Calc Calculate in Parallel", LibOCon 2017 slides](https://conference.libreoffice.org/assets/Conference/Rome/Slides/libocon-2017-novideos.pdf)). Well-sourced for existence; fine details = source-level.

## 4. Web grid rendering at scale

- **Google Sheets has always been canvas-rendered** (tech shared with Maps-era tiling); Docs followed in 2021 for performance/consistency. Well-sourced: [Workspace announcement](https://workspaceupdates.googleblog.com/2021/05/Google-Docs-Canvas-Based-Rendering-Update.html), [The New Stack](https://thenewstack.io/google-docs-switches-to-canvas-rendering-sidelining-the-dom/).
- **Glide Data Grid:** abandoned DOM virtualization (react-virtualized) because mounting/unmounting hundreds of DOM nodes per frame can't hold 60fps; draws only visible cells to canvas with **damage tracking** for partial repaints; flat memory vs row count; millions-of-rows demo. Well-sourced: [repo](https://github.com/glideapps/glide-data-grid), [1M-row demo](https://glideapps.github.io/glide-data-grid/?path=/story/glide-data-grid-dataeditor-demos--one-million-rows).
- **Tile/chunk persistence + streaming design (informal but quantitative):** event-sourced log + immutable LSM-style segments of ~1MB chunks (~28K cells/chunk at 37B/cell); 2-D tiling via variable-width column stripes × variable-height tiles; two-stage binary-search index reaches any cell in ≤4 chunk fetches at extreme grid sizes. Well-sourced as a published design study: [Brainstorming and Benchmarking](https://www.thecandidstartup.org/2023/02/27/brainstorming-and-benchmarking.html), [Snapshot Data Structures](https://www.thecandidstartup.org/2023/05/01/spreadsheet-snapshot-data-structures.html), [Insert/Delete](https://www.thecandidstartup.org/2023/06/05/spreadsheet-insert-delete.html).

## 5. Template compression & corpora

- **Enron corpus:** 15,770 sheets; 97.6M non-empty cells; **20,277,835 formulas but only 913,472 unique by relative-R1C1 equality (~4.5%)** — direct quantitative support for template-region compression. Well-sourced: [Hermans & Murphy-Hill dataset paper](https://www.researchgate.net/publication/304552688_Enron's_Spreadsheets_and_Related_Emails_A_Dataset_and_Analysis), [Enron vs EUSES comparison](https://arxiv.org/pdf/1503.04055). **FUSE:** 249,376 sheets, 8.5M unique formulas across EUSES+Enron+FUSE used in grammar studies: [FUSE](https://www.researchgate.net/publication/308861425_Fuse_A_Reproducible_Extendable_Internet-Scale_Corpus_of_Spreadsheets), [XLParser grammar paper](https://aivaloglou.org/wp-content/uploads/2019/04/smrdoc.pdf).
- **TACO (VLDB 2023): compressed formula dependency graphs** via "tabular locality" patterns (four edge patterns, incl. relative-relative chains); answers precedent/dependent queries *directly on the compressed graph* and maintains it incrementally; up to 34,972× vs uncompressed framework, 632× vs commercial systems. The closest academic analogue to a compressed dependency layer over template regions. Well-sourced: [arXiv 2302.05482](https://arxiv.org/abs/2302.05482); companion visualization at [VLDB vol16 p4030](https://www.vldb.org/pvldb/vol16/p4030-tang.pdf).
- **DataSpread (UIUC/Berkeley):** spreadsheet-on-RDBMS; **recursive decomposition of a sheet into hybrid dense (ROM/table) and sparse regions** (20-50% storage, up to 50% formula-eval savings vs single primitive model) + **hierarchical positional mapping** (counted B-tree-style) so row insert/delete is O(log n) instead of renumbering — directly relevant to sparse block occupancy + 1M-row addressing. Well-sourced: [arXiv 1708.06712](https://arxiv.org/pdf/1708.06712), [billions-of-cells paper](https://people.eecs.berkeley.edu/~adityagp/dataspread.pdf). Their later "Anti-freeze" asynchronous-computation work covers visibility-prioritized recalc (inference: same group; verify title before citing).

## 6. Verification / equivalence prior art

- **Microsoft's Calc.ts:** MSR wrote a *written semantics for Excel plus a TypeScript reference implementation of formula evaluation*, explicitly because "the only precise documentation of Excel semantics is its source code" — strongest industrial precedent for a simple-correct reference paired with the optimized engine. Well-sourced: [LAMBDA blog post, MSR](https://www.microsoft.com/en-us/research/blog/lambda-the-ultimatae-excel-worksheet-function/).
- **Sestoft/Funcalc operational semantics:** published big-step semantics for formulas, array formulas, SDFs, with *two implementations (interpreter vs runtime codegen) validated against the same semantics*: [Bock et al., On the Semantics for Spreadsheets with Sheet-Defined Functions](https://www.sciencedirect.com/science/article/pii/S2590118420300204); cost semantics variant at [Aalborg](https://vbn.aau.dk/en/publications/concrete-and-abstract-cost-semantics-for-spreadsheets). Corecalc itself is positioned as an experimentation/reference platform (tech report preface).
- **Differential testing generally** (cross-engine oracles; reference-implementation-as-oracle) is standard methodology but I found **no published spreadsheet-engine-specific differential-testing paper**; engines in practice use Excel-roundtrip corpora as oracles (inference from SheetJS/LibreOffice test suites). General background: [Differential testing (Wikipedia)](https://en.wikipedia.org/wiki/Differential_testing).

**Confidence notes:** Excel chain/MTR/LAA, xlsx shared formulas, Sestoft FAP-set support graph, Enron uniqueness stats, TACO, DataSpread, HyperFormula range decomposition, Glide canvas rationale, Calc.ts = well-sourced. IronCalc internals, LibreOffice formula-group fine detail, Anti-freeze paper title = inference/needs source-level verification.
